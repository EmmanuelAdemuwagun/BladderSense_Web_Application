System Architecture · Proof of Concept

BladderSense Web Application

A mobile-first, senior-friendly React SPA delivering a bladder-health guide for older men — passwordless email auth, a 12-section guidebook, a daily symptom diary, and a 30-day progress view. Static front end on Netlify, stateful API on Heroku, joined by a cookie-preserving reverse proxy.

01

High-Level Architecture

The browser talks only to bladdersense.com. Netlify serves the static app and reverse-proxies /api/* to the Heroku backend — the one move that keeps the session cookie first-party so it survives iOS Safari's tracking protection.

Active request path & auth Persistent data Infrastructure Legacy / not on live path
Key decision

The backend lives on a different origin (Heroku). A direct browser→Heroku call would set a third-party cookie, which iOS WebKit + Intelligent Tracking Prevention silently drop — bouncing users back to sign-in. Routing every call through Netlify's /api/* proxy makes them same-origin, so the cookie persists first-party. This requires the backend to set a host-only cookie (no Domain=…herokuapp.com) so the proxy can re-attribute it.

Two backends

The repo carries two backend implementations. The live one is the Heroku API above (cookie sessions, documented in docs/backend-requirements.md). The netlify/functions/* serverless set is an earlier PoC iteration — Bearer tokens + JSONBin/JSON files — that the current front end no longer calls. The README.md still describes that older model.

Low-Level Architecture — Front End

Boot path and module dependencies. content/ is pure data feeding the pages; utils/ is the seam to the network and the local display hint; seo.mjs is a single source of truth shared by the runtime and the build-time prerender.

03

The Auth Model

Authentication is entirely server-side. The browser holds no token; client-side "gating" is optimistic and self-healing.

Source of truth

Heroku API

  • HttpOnly cookie bladdersense_session
  • Secure, SameSite=Lax, host-only
  • Sent automatically via credentials:"include"
  • The client can't read or forge it

Local display hint

utils/auth.js · localStorage["gbapp_user"]

  • Stores only {id, name, email}
  • Used for instant greeting / initials
  • Not an auth secret — old token code is disabled
  • Cleared whenever the server returns 401

Optimistic gating

Dashboard.jsx · GuideSection.jsx

  • Paint from hint (fast first frame)
  • Then call api.getProfile() as the probe
  • 200 → stay · refresh hint
  • 401 → clearSession() → /signin
04

Passwordless Sign-In Flow

Registration mirrors this with a link + emailVerified flag. The login-request response is intentionally neutral to resist account enumeration.

1

Request a code

User enters email → api.requestLoginToken → POST /auth/request-login. Backend emails a 6-char code ([A-Z0-9]{6}, expires in minutes) — only if the account exists and is verified. Response is neutral either way.

2

Verify the code

User enters code → api.verifyLoginToken → POST /auth/verify-login. Backend validates and issues Set-Cookie: bladdersense_session (HttpOnly · Secure · host-only).

3

Land signed in

Response returns the safe user object → saveSession() writes the local display hint → navigate("/dashboard"). Every later request carries the cookie automatically.

4

Stay verified

Each gated page re-probes with api.getProfile(). A 401 anywhere clears the hint and bounces to sign-in — so an expired cookie can never leave a stale session on screen.

05

API Surface

Every method in src/utils/api.js, base path /api, all through one request() wrapper (JSON · credentials included · throws the server's {error} text).

MethodEndpointPurpose
POST/auth/registerCreate account, email verification code
POST/auth/verify-emailConfirm email with code
POST/auth/resend-verificationRe-send verification code
POST/auth/request-loginEmail a 6-char sign-in code

POST/auth/logoutClear the session cookie
GET/profileCurrent user — also the auth probe

DELETE/profileDelete account
GET/trackingList entries (newest first, 30-day window)
POST/trackingCreate one entry (one per day; 409 if exists)
PUT/tracking/:idEdit an existing entry
Data contract

Tracking fields are string enums the backend validates case-sensitively: nightTimeUrination (0·1·2·3+), eveningFluids (None·Small·Moderate·Large), activityLevel (None·Light·Moderate·High), stressLevel (1–5), sleepQuality (Poor·Fair·Good), plus optional notes and an entryDate. A /tracking/summary endpoint powers the monthly progress view; reminders are delivered by email, not native push.
